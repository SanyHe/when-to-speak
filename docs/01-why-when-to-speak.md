# 为什么是「When to Speak」

> 一个 always-on agent 最难的不是"能做什么"，而是"**什么时候该开口**"。

## 1. 问题

想象一个持续在线的个人助理：它读邮件、看 IM、跑后台任务、定时巡检。它每小时能产生几十条候选事件，但用户一天真正需要被打断的时刻可能只有两三次。

于是问题变成：

> 给定一个事件及其上下文，**该不该现在打扰用户？该走什么渠道？该说什么？** 如果没有值得说的内容，就应该保持静默。

这不是一个"聊天能力"问题，而是一个**注意力分配**问题。它有三个特征：

- **代价不对称**：漏掉 P0 故障的代价很高，但一天误打扰二十次的代价同样高——后者会直接导致用户关掉通知、弃用产品。
- **上下文依赖**：同一条消息，在用户空闲时需要通知，在深度工作时也许只配进入汇总；群发营销邮件则永远应该静默。
- **可量化**：可以定义 precision / recall、噪音率、漏报率，用数字而非感觉来判断一个 agent 是否"懂事"。

## 2. 为什么它值得做成一个 Demo

主流 demo 大多是"风格克隆聊天机器人"：换个语气说话，很难看出工程深度。本选题相反：

| 维度 | 说明 |
|---|---|
| 研究感 | 对应 Lee Robinson 在 Stanford CS146S 点名的开放问题之一（When to Speak），不是伪需求。 |
| 可学性 | 输出是结构化三分类，0.6B 小模型就能学会，训练成本低、可复现。 |
| 可评测 | 有明确的 gold label 与指标，不靠主观"感觉不错"。 |
| 可展示 | base / SFT / SFT+GRPO 三模型在同一事件流上的行为反差非常直观。 |
| 可讲回主线 | 通知成本、误打扰成本、空闲 agent 的算力成本，都能自然接到推理 FinOps 的话题。 |

## 3. 任务定义

- **输入**：一条事件 `event`（来源、发件人、主题、摘要、是否 @ 用户、是否直达、是否时效性强、用户当前状态、最近通知数、是否重复）。
- **输出**：一个严格 JSON `decision`：

```json
{
  "action": "notify | digest | silence",
  "channel": "im | email | push | none",
  "urgency": "urgent | normal | low",
  "reason": "一句话理由",
  "message": "通知文案；silence 时为空字符串"
}
```

三档动作的含义：

- `notify`：立即打断，只留给高时效、高重要性、直接关联用户的事件。
- `digest`：不单独打扰，进入周期性汇总。
- `silence`：完全静默，用于营销群发、重复事件、例行自动化通知等。

## 4. 成功标准

后训练的目标不是"更会说话"，而是：

> 在**显著降低噪音率**的同时，**漏报率不上升**；并且输出必须是稳定可解析的严格 JSON。

这条标准贯穿数据、训练、评测与网页交付，也是本项目所有里程碑的验收依据。

## 5. 范围边界

- 本期只用**合成数据**，不接入任何真实邮件 / IM，因此可以公开、无隐私风险。
- 后训练链路为**全参 SFT + GRPO**；更复杂的 RL（PPO / 多轮环境）留作后续。
- 网页端用 WebLLM + WebGPU 在访客本机推理，零后端、零 API Key。
